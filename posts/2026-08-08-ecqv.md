## A token nobody wanted to read

Filament mints invitations. You run one command, it prints a code, and someone on
another machine claims it and joins your fleet with a bounded set of capabilities. The
token is self-contained: it carries the capability ceiling, an expiry, an offline
budget, and a signature, so the receiving side can check it without asking a server
anything.

The first version was 780 characters.

Nobody reads 780 characters. They paste it, and if it does not paste cleanly they give
up. The QR encoding of it was 104 columns wide, which does not fit a terminal, and the
error correction had been quietly lowered to buy back the columns, which is the kind of
compromise that survives long after anyone remembers making it.

So I went looking for the bytes. Most of them were not bytes at all. The token was JSON
with hex-encoded binary fields, then base64 over the top, which is three layers each
paying for the last: hex doubles every key and signature, JSON repeats the field names
in every token, base64 adds a third again. The *content* was about 116 bytes. The
encoding was the other three quarters.

Fixing the encoding got it to 184 characters, and the QR to 68 columns with the error
correction restored. That is a good day's work and it is not what this post is about.

What this post is about is the next question, the one that has no boring answer: what is
the *floor*? If you strip every wasted byte, how small can a self-contained,
offline-verifiable capability token actually be?

---

## The floor, and what sets it

Count what has to be there.

An Ed25519 signature is 64 bytes. That is not negotiable; it is what a signature costs.
The enrollment key is 32. You need a few bytes to say which issuer signed this, and a
few more for the capability bits, the expiry, the budget. Call the whole thing 116
bytes, which is 155 characters in base64url.

So: 780 to 155, and *more than half of what remains is the signature*.

That reframes the problem. Any further compression is not a question about encoding. It
is a question about the signature, and there are only so many things you can do to a
signature. You cannot compress it, because a signature is indistinguishable from random
noise by construction, and if it were compressible that would be a break in the
cryptosystem rather than a saving. You cannot truncate it. You could use a scheme with
a shorter signature, but the exotic ones buy you sixteen bytes and cost you every
audited implementation.

Or you could ask whether you need a signature at all.

## What an implicit certificate is

Here is the ordinary shape. A certificate authority wants to attest that some public
key belongs to some identity. It takes the key, takes the identity, and signs both. The
certificate is *key plus identity plus signature*, and anyone who trusts the CA's public
key can verify it. That costs you 32 bytes for the key and 64 for the signature before
you have said anything about who the holder is.

An implicit certificate does something else. The certificate is a single elliptic curve
point, 33 bytes compressed, and it contains neither the public key nor a signature.
Instead, anyone can *reconstruct* the holder's public key from that point plus the CA's
public key:

```
Q_U = e · P_U + Q_CA          where e = H(certificate)
```

The holder, and only the holder, can compute the matching private key, because the CA
sent them a private contribution that nobody else saw. So the certificate is not a
statement *about* a key. The certificate is the thing the key is derived *from*.

Ninety-six bytes become thirty-three. The scheme is ECQV, standardised as SEC 4, and it
is not a curiosity: it is deployed in IEEE 1609.2, which is the security layer for
vehicle-to-vehicle communication, and in ZigBee Smart Energy. It exists because those
systems count bytes the way filament was counting characters, and for the same reason,
which is that a radio link and a terminal window are both narrower than anyone would
like.

---

## The catch, which is the whole scheme

There is no verification step.

I want to be precise about this, because it sounds like a gap in my explanation and it
is not. In an ordinary certificate you check the signature and get a yes or a no. In
ECQV there is nothing to check. You reconstruct a public key, and reconstruction
*always succeeds*. Feed it a certificate forged by someone with no relationship to the
CA and it will hand you a public key with no complaint at all.

What you get back from a forged certificate is simply *the wrong key*. It will not
verify any signature the real holder produced. It will not complete a key agreement
that the real holder could complete. It is a perfectly well-formed point on the curve
that is useless for everything, and the only way you discover this is by trying to use
it and watching that fail.

This is called implicit validation, and it is not a flaw. It is the mechanism. The 63
bytes you saved were the bytes that would have told you *up front* whether the
certificate was genuine, and the trade is that you find out later instead, as a side
effect of the key working or not working.

For a V2X radio that is a fine trade. Every message is signed anyway, so the
verification you were already doing is the validation, and you have paid nothing.

## Why I argued against it

Filament had spent the previous night on a bug.

The short version: revocation was not binding on one of the transports. A device you had
explicitly revoked could complete a transfer, because on that path the receiver never
resolved the sender's identity, and the gate cannot deny a device it cannot name. The
fix was to issue an identity challenge on that transport and hold the transfer until
identity settled.

Read that back with implicit certificates in mind.

The bug was a gate acting on a peer whose identity had not yet resolved. Implicit
validation makes *not yet resolved* the normal state, for longer, by design. There is no
moment where a function returns "this certificate is valid" and the code can branch on
it. There is only a key that has not yet failed.

That is a fine property in a system built around it, where every path exercises the key
and a wrong key is caught immediately. It is a dangerous property to introduce into a
system that has just demonstrated it can act too early, in a hand-rolled implementation
of a scheme with few audited precedents, to save 63 bytes on a token that had already
come down from 780 to 184.

So I said no. The token stays Ed25519, the signature stays 64 bytes, and the 184
characters are good enough.

## And then built it anyway

The objection was about *filament*, not about ECQV.

There is no good Rust implementation of SEC 4 ECQV. The scheme is deployed in real
systems, the standard is public, and anyone in the Rust ecosystem who needs it today is
either writing it themselves or binding to C. That is a gap worth filling, and filling
it badly is worse than leaving it, which is most of what shaped the work.

Three decisions carried the weight.

**Build the protocol, not the arithmetic.** The crate sits on RustCrypto's `p256` and
`elliptic-curve`. Those give constant-time field operations, subgroup validation, and
SEC1 encoding, reviewed by people who do this professionally. ECQV on top of them is
about two hundred lines. Reimplementing P-256 underneath would have been the single
most likely way to produce something confidently broken.

**Get real test vectors, and check them before trusting them.** SEC 4 publishes none, a
fact I had assumed the opposite of and was corrected on. The usable set comes from
CAMP's work on the V2X credential management system, and it covers the CA side, the
requester side, and reconstruction *separately*, which matters because a vector set that
only checks the round trip cannot tell you which half is wrong. Every output in those
vectors was re-derived from the raw inputs with independent arithmetic before any of
them were allowed near the test suite. "The vectors agree with my code" and "the vectors
are correct and my code agrees" are different claims, and only the second one is worth
anything.

That paid immediately. The first hash-to-scalar implementation truncated the digest by
clearing its top bit. SEC 4 wants the leftmost 255 bits, which as an integer is the
digest shifted right by one, not masked at the top. Same bit count, different number,
and it would have survived any amount of code review while failing every vector. The
harness caught it before a single deliberate bug had been planted to test the harness.

**Put the hazard in the type system.** This is the part I care about most, because it is
the part that decides whether the library is safe for someone who has not read this
post.

Reconstruction does not return a public key. It returns an `UnvalidatedPublicKey`, and
the only thing you can do with it that *succeeds* is an operation that proves the key
works, which in practice means verifying a signature the holder produced. There is an
escape hatch, because sometimes you genuinely need the bare key, and it is called
`into_public_key_unchecked`, with the `_unchecked` suffix that Rust programmers already
read as "you are taking responsibility" and that an auditor can grep for across an
entire ecosystem.

The escape hatch documents the thing that is easiest to get wrong. Using the bare key
for key agreement does *not* validate the certificate. A forged certificate produces a
shared secret that the peer does not share, and nothing fails at that moment; it fails
later, when something authenticated with that secret does not decrypt, if anything
does. Deferred validation is still validation, but only if something downstream is
actually doing it.

None of that is in the standard. The standard describes a scheme. The API is where you
decide whether the scheme's sharp edge is pointed at your users.

---

## What it is not

It is not an IEEE 1609.2 implementation, and if you arrived from V2X that is the
sentence to read twice. 1609.2 uses ECQV over a different certificate encoding with a
different hash structure. The crate implements the SEC 4 protocol core with a pluggable
encoding layer, so a 1609.2 module could sit on top of it, but that module does not
exist and pretending otherwise would waste somebody's afternoon.

It is also not audited. It is validated against known-answer vectors that were
independently re-derived, it has no unsafe code, it is `no_std`, and none of that is an
audit. The README says so in the first section, before anything else, because the
audit status is exactly the thing a reader must not have to go looking for.

## The thing I keep relearning

Both halves of this were the same judgement.

Not putting ECQV into filament was not caution about ECQV. It was a specific claim: that
a scheme whose defining property is *validation happens later* should not be introduced
into a codebase that had just shipped a bug caused by acting before validation had
happened. The 63 bytes were real and the risk was more real.

Building the library was the same judgement pointed the other way. The scheme is
genuinely good, the gap in the ecosystem is genuinely there, and the reason to be
careful about deploying it is a reason to *understand* it, not to avoid it.

The crate is [ecqv](https://crates.io/crates/ecqv). The token in filament is still 184
characters, still Ed25519, and I am still glad about both.
