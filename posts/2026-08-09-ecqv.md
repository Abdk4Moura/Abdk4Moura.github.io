## Where this started

I started filament first as an experiment, looking to implement a p2p file service myself. But I thought the p2p idea, and the ideas marinating in that space, were not being appreciated or utilised enough, and it occurred to me that we could make Tailscale simpler and even more private. So I set out to do that.

The undesirable part of Tailscale is how heavily it relies on the coordination server. A compromised coordination server is a compromised system. That is not a bug in their implementation, it is what the architecture asks of you: you trust the coordinator, and in exchange it does the hard part of finding your peers for you.

So the thing to eliminate was the persistent reliance on a central coordinator. Not the coordinator itself, which is genuinely useful for introductions, but the *dependence* on it. We give you a default bootstrap to fall back on, and we let you point it at something else if you would rather. And we made the coordination server a dumb pipe: it cannot man-in-the-middle you, and the worst a malicious one can do is refuse to introduce you. Denial of service, not a security hole.

How do you get that? PAKE.

## The ritual

A password-authenticated key exchange is essentially a Diffie-Hellman type initiation where we make the two peers go through a ritual. The coordination server watches the whole thing, and, exactly as in classic Diffie-Hellman, it can do nothing with what it sees. When the ritual finishes the two peers have a shared key that the observer does not have, and from there they establish a direct link and stop needing the server at all.

I was not the first person to notice this. It turned out magic-wormhole was already using PAKE for exactly this kind of tunnelling, and croc after it, and when I found that I thought it was brilliant. Two people read a short code aloud, and out of that comes a channel nobody else can enter. The code is short enough to say over a phone call and the exchange is still safe, which is the part that feels like cheating the first time you see it.

What occurred to me is that there are a lot of benefits to a p2p link beyond moving one file. So: why not use this for a pairwise VPN? There is nothing new about that idea, I reckon, since it is essentially what Tailscale is doing. But do it over a ritual that leaves the coordinator blind, and let any publicly available node act as the coordinator, and the central dependency goes away.

That is the shape: a decentralised model where the introduction is cheap and replaceable, and where every device has a key.

## Why keys, and then why certificates

Once every device has a key, a question arrives that the file-transfer case lets you avoid.

For one transfer between two people reading a code aloud, you do not need to know who anyone is. The code *is* the authorisation. It was said out loud, once, to one person, and when the transfer is done the authority it carried is spent.

A mesh is not like that. A mesh has devices that keep existing, that reconnect tomorrow, that should still be recognised without anyone reading anything aloud again. And the moment you want *that*, you need to answer a question the code never had to: when this thing reconnects, how do I know it is the same thing?

A public key answers it. The device holds a private key, proves possession of it, and I recognise the corresponding public key. Good. But it produces the next question immediately, and this is the one that runs the rest of this post: how do I know *that public key* belongs to a device I actually let in?

Anyone can generate a key pair. Generating one is free. If recognition means "I have seen this key before", then anyone who wants to be recognised simply makes a key and claims to be someone, and if they want to be a thousand devices they make a thousand keys. That is a Sybil attack, and it is cheap precisely because key generation is cheap.

What stops it is that the keys have to come from somewhere I trust. Not "I have seen this key", but "someone I already trust vouched for this key." That someone is a certificate authority, and in filament it is you: your identity key signs your devices into your own mesh. A device is not in because it has a key. It is in because your key said so.

That is why certificates showed up in a peer-to-peer file transfer program. Not because we wanted PKI, which nobody wants, but because "no central coordinator" plus "devices that persist" adds up to needing a local authority, and the local authority is you.

## And then the certificates were too big

Here is the part where the theory ran into a number.

We found our auth keys and secrets were too long. Over 500 bytes. My own reaction on first seeing one printed in a terminal was that it was too, too, too long: I had expected something like a Tailscale auth key, which is about fifty characters, and this was way past that. In practice it meant a token you paste rather than read, a QR code too wide for a terminal window, and the general feeling that the security was showing through the product in a way it should not.

So we went looking for very byte-efficient security measures, and for more ingenious ways to compress the thing.

Count what a normal certificate has to carry. There is the identity, which you cannot avoid. There is the public key, which is 32 bytes compressed. And there is the CA's signature over both, which is 64 bytes. That is 96 bytes of overhead before you have said anything anyone cares about, and none of it is your message. It is the paperwork proving you are allowed to send the message.

## Where the bytes actually were

Before going looking for clever mathematics I should have looked at the packaging, and when I did, most of the problem was there.

The token was JSON, with the binary fields hex-encoded, and then base64 over the whole thing. Three layers each paying for the last. Hex spends two characters on every byte, so the 64-byte signature alone cost 128 characters and the keys another 64 each. JSON repeats the field names in full in every single token. Then base64 adds a third on top of all of it.

The actual content was about 116 bytes. Everything else was wrapping. Fixing the encoding took the token from 780 characters to 184, and the QR from 104 columns down to 68, which fits a terminal. That is a good afternoon and it is not interesting.

What was interesting is the question it left behind: if you strip every wasted byte, how small can this thing actually get?

Count what has to be there. The signature is 64 bytes, because that is what an Ed25519 signature costs. The enrollment key is 32. You need a few bytes to say which issuer signed this, and a few more for the capability bits and the expiry and the budget. Call it 116 bytes, which is about 155 characters once encoded properly.

So the floor is 155, and **more than half of what remains is the signature**.

## Why you cannot compress your way out

My first instinct was compression, and the question I kept circling was whether there was something clever left to do, or whether the thing was simply incompressible because of high entropy.

It is the second one, and it is worth saying why, because the answer is more interesting than a no.

You cannot compress a signature. Not "it compresses badly", not "the gains are small". You cannot do it, and the reason is that a signature is *supposed* to be indistinguishable from random noise. Compression works by finding structure and describing it more briefly. A cryptographic output with findable structure is a broken cryptographic output. So if you handed me a compressor that reliably shrank Ed25519 signatures, I would not have a smaller token, I would have a paper about a weakness in Ed25519.

The same goes for the key material. High entropy is the property we are paying for, and entropy is exactly what refuses to compress. gzip would have crushed the JSON and the hex, because those are structure, but structure was never the expensive part after the encoding fix. Once you are at the floor, compression has nothing left to work with.

Which reframes the whole problem. Below 155 characters, this stops being a question about *how the information is written down* and becomes a question about *what information has to be there at all*. And since half the remainder is the signature, it becomes a question about the signature specifically.

## Everything I tried before ECQV

So if the bytes will not compress, the ingenuity has to go somewhere else: into what the token needs to contain at all. Here is everything I considered, and why each one died.

**Use a MAC instead of a signature.** A MAC is 16 bytes where a signature is 64, so this was the biggest single prize on the table. It fails for a structural reason. A signature exists so that a *third party* can verify. A MAC can only be checked by someone holding the same secret that produced it. In filament the thing verifying an invitation is a device holding only the owner's *public* key, so switching to a MAC would mean handing every verifier the owner's secret, and any device that can verify could then also mint. That is not a smaller token, it is a different and much worse trust model.

**Use a scheme with shorter signatures.** BLS gives you 48 bytes compressed instead of 64. Sixteen bytes, in exchange for leaving behind every audited, widely-reviewed implementation in the ecosystem and taking on pairing arithmetic. Bad trade for a QR code.

**Truncate the signature.** No.

**Make the token a handle, the way Tailscale does.** A Tailscale auth key is about fifty characters, and it is short because it is not self-contained: it is a random identifier, and the coordination server holds all the meaning. You could do that, and the token would be tiny, and you would have traded away exactly the property this whole project exists for. Our token is checkable with no server involved. Handing the capability metadata to a coordinator to hold on our behalf reintroduces the dependency I started out trying to remove.

**Hash-pinned handle, as a middle path.** This one I actually liked. The token carries a short random identifier plus a 128-bit hash of the capability blob; the blob itself travels over the signalling channel; the claiming device verifies the blob against the hash before trusting it. Around 43 characters, and the server cannot forge anything, because forging would mean breaking the hash. What it can do is read the blob, and withhold it. So the cost is not cryptographic assurance, it is a positioning claim: "no key crosses the server" would become "a hash-pinned blob crosses the server". That is a real thing to give up and I did not want to give it up for 112 characters.

Which leaves exactly one door. Every option above tries to make the signature smaller or move it somewhere else. The remaining question is the one that sounds like a riddle: **what if there were no signature?**

## Somebody had already asked it

They had, decades ago, and we chanced upon it for the same reason it was created.

The scheme is called ECQV, for Elliptic Curve Qu-Vanstone, after Minghua Qu and Scott Vanstone at Certicom, and it is standardised as SEC 4. What they were looking at was vehicle-to-vehicle safety radio: every car announcing its position, speed and heading, ten times a second, continuously, every car in range. Each message must be authenticated or someone spoofs a phantom truck at an intersection. The safety payload is tens of bytes. The certificate is 96 or more.

The paperwork is bigger than the message. In dense traffic that is what fills the channel, not the data anyone cares about. They could not shrink the signature and they could not broadcast less often, because that is the safety requirement. The only thing left to attack was the certificate itself.

So ECQV was not invented to be elegant. It was invented because a radio channel filled up. We arrived at the same door from a QR code that would not fit in a terminal window, which is a far smaller problem with exactly the same shape.

## The trick

An implicit certificate contains neither the public key nor a signature.

What it contains is one point on the curve, the public key reconstruction value $P_U$, 33 bytes compressed. From that point, plus the CA's public key $Q_{CA}$, anyone can *reconstruct* the holder's public key $Q_U$:

$$Q_U = e \cdot P_U + Q_{CA} \qquad \text{where } e = H(Cert_U)$$

And the holder, and only the holder, can compute the matching private key, because the CA sent them a private contribution nobody else saw.

Ninety-six bytes become thirty-three.

The paradigm shift is worth sitting with, because it is not a compression trick. In the ordinary scheme the certificate is a *statement about* a key: here is a key, and here is my signature saying it belongs to this person. In ECQV the certificate is the thing the key is *derived from*. There is no statement. There is a starting point, and following it either gets you somewhere real or it does not.

Which means the certification is not a check you perform. The certification is *whether a particular action becomes possible*.

The logic runs like this. Let me derive $Q_U$ from the certificate data and the CA key. Now let me verify the message signature using $Q_U$. If it works, then the message is authentic and the certificate is valid, and both are proven simultaneously by the same operation. If it fails, then either the message was tampered with or the certificate was fake, and either way I drop the packet.

You never asked "is this certificate good?" You asked "does this work?", and the answer covered both questions at once.

For the radio that is perfect. The safety message is signed anyway, so the verification you were already doing *is* the validation, and the certificate check costs you nothing on top. That is the second half of why the scheme is small: it does not just shrink the bytes, it folds two operations into one.

## The catch, which is the same fact

Reconstruction always succeeds.

Feed it a certificate forged by a total stranger and it will hand you a public key with no complaint at all. What you get is simply the wrong key: a well-formed point on the curve that is useless for everything, and the only way you find out is by trying to use it and watching that fail.

That is implicit validation, and it is not a flaw. It is the mechanism. The 63 bytes you saved were exactly the bytes that would have told you up front, and the trade is that you find out later instead, as a side effect.

Everything depends on whether "later" is guaranteed to arrive. In V2X it is, because every message is signed and every signature is checked. In a system where some code path might reconstruct a key and simply believe it, the trade is a bad one and nobody will notice it is bad, because a forged certificate does not error. It just quietly produces a key that does not work, somewhere else, later.

## Why it is not in filament

I built the library and then argued against using it here, and both of those were the right call for the same reason.

The night before I looked seriously at adopting it, filament had a revocation bug. A device that had been explicitly revoked could still complete a transfer, because on one transport the receiver never resolved the sender's identity, and a gate cannot deny a device it cannot name. The fix was to issue the identity challenge on that transport and hold the transfer until identity settles.

Now read implicit validation with that fresh in mind. The bug was a gate acting on a peer whose identity had not resolved. Implicit validation makes "not yet resolved" the normal state, by design, for longer. There is no moment where something returns *valid* and you branch on it. There is only a key that has not failed yet.

That is a fine property in a system built around it. It is a dangerous property to add to a codebase that had just demonstrated it can act too early, in a hand-rolled implementation of a scheme with few audited precedents, to save 63 bytes on a token that had already come down from 780 characters to 184 by fixing the encoding.

The encoding, incidentally, was most of the problem all along. The token was JSON with hex-encoded binary fields and then base64 over the top: three layers each paying for the last. The actual content was about 116 bytes and the rest was packaging. Fixing that got the QR into a terminal without touching the mathematics.

So the answer was no, for filament. The token stays Ed25519, the signature stays 64 bytes, and I am glad about both.

## But the library should exist

The objection was about filament, not about ECQV.

There was no good Rust implementation of SEC 4 ECQV. Some of the mathematics existed elsewhere: schnorrkel has an implicit certificate scheme, though on Ristretto255 via Schnorr adaptor signatures rather than SEC 4 on a prime curve, aimed at Polkadot rather than at V2X. libsm implements SM2, which shares the structural idea. Zenroom has had ECQV since 2018 with C bindings you can reach from Rust. But if you wanted the actual standard, on a NIST curve, natively, you were writing it yourself or binding to C.

Three decisions shaped how I built it.

**Build the protocol, not the arithmetic.** It sits on RustCrypto's `p256` and `elliptic-curve`, which give constant-time field operations, subgroup validation and SEC1 encoding, all reviewed by people who do this professionally. ECQV on top of that is about two hundred lines. Reimplementing P-256 underneath would have been the single most reliable way to produce something confidently broken.

**Get real vectors, and check them before trusting them.** SEC 4 publishes none, which I had assumed the opposite of. The usable set comes from CAMP's work on the V2X credential system, and it covers the CA side, the requester side and reconstruction separately, which matters because a vector set that only checks the round trip cannot tell you which half is wrong. Every output was re-derived from the raw inputs with independent arithmetic before any of them went near the test suite. "The vectors agree with my code" and "the vectors are correct and my code agrees" are different claims and only the second is worth anything.

That paid immediately. The first hash-to-scalar implementation truncated the digest by clearing its top bit. SEC 4 wants the leftmost 255 bits, which as an integer is the digest shifted right by one, not masked at the top. Same bit count, different number, and it would have survived any amount of reading. The harness caught it before a single deliberate bug had been planted to test the harness.

**Put the hazard in the type system.** Reconstruction does not return a public key. It returns an `UnvalidatedPublicKey`, and the only thing you can do with it that succeeds is an operation that proves the key works. There is an escape hatch, because sometimes you genuinely need the bare key, and it is called `into_public_key_unchecked`, with the suffix Rust programmers already read as *you are taking responsibility* and that an auditor can grep for across a whole ecosystem.

The escape hatch carries the warning that matters most: using the bare key for key agreement does *not* validate the certificate. A forged certificate produces a shared secret the peer does not share, and nothing fails at that moment. It fails later, when something authenticated with that secret does not decrypt, if anything checks.

None of that is in the standard. The standard describes a scheme. The API is where you decide whether the scheme's sharp edge is pointed at the people using it.

## What it is not

It is not an IEEE 1609.2 implementation. 1609.2 uses ECQV over a different certificate encoding with a different hash structure, so a module for it could sit on the pluggable encoding layer, but that module does not exist. If you came here from V2X, that is the sentence to read twice.

It is not audited. It is validated against independently re-derived known-answer vectors, it has no unsafe code, it is `no_std`, and none of that is an audit.

It is P-256 only, deliberately.

The crate is [ecqv](https://crates.io/crates/ecqv).
