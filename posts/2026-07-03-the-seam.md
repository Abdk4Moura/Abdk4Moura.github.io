## The format-contract assumption

Routing a coding agent to a different model is supposed to be a model swap. You set a
base URL, you point the client at it, the chat text moves, and you go. The present
wave of *model routers* for Claude Code, OpenCode, and the rest is built on that
assumption: that what the client emits and what the model speaks are *almost the same
thing*, and the gap between them is a thin shim that someone has already written.

I think this assumption is wrong, and the whole bet of `claude-go` is that it is wrong
in a particular place. The interesting boundary in routing Claude Code to a
non-Anthropic model is not the model's text, it is the *tool call*. The model emits a
structured instruction, *run this command, edit this file, read these lines back*, and
the runtime hands it the world and asks the model to look at what came back. That is
where the agent reasons. Break the round-trip and the model loses the thread; keep it
faithful and the model can keep thinking, and the chat text is almost an afterthought.

So the design choice that `claude-go` makes is not about which model to support. It is
about *where the seam lives*, and the claim is that the seam should be invisible to the
agent on the other side. Said plainly, the agent should not be able to tell that it is
not talking to the canonical backend, and an in-process proxy is the design choice that
makes that tractable.

This is a post about that seam.

---

## Where the seam lives

To talk to a model, a client and a server have to agree on a *shape*. Anthropic's
shape is **Messages**: a stream of typed blocks, *system*, *user*, *assistant*,
*tool_use*, *tool_result*, each with a defined JSON schema, and a strict contract
about how the blocks turn into a request and how the response turns back into a
conversation. The shape every other model speaks, OpenAI's **Chat Completions** being
the canonical example, is different. Different block names, different role names, a
different way of carrying a tool call and its result.

The seam is the boundary where the two shapes meet. Every model router for Claude Code
has one, because every model that is not Anthropic speaks something else. The seam
takes a Messages request, asks the other model in its own dialect, and returns a
Messages response the client can consume unchanged. The router that does this well is
invisible. The router that does it badly is a translation layer that the agent, sooner
or later, notices.

Call this boundary the *seam*, and the claim of this post is that the seam is where
the design lives, not the model selection. The interesting question is not *which
model* a router supports. It is whether the seam carries the *thinking* of an agent
across, or only its text.

---

## Why the seam is load-bearing

The reason the seam is load-bearing is that an agent does almost all of its reasoning
inside the tool-use round-trip, and almost none of it in chat text. Consider the
shape of a coding task. The model emits a `tool_use` block to run a command. The
runtime executes the command and returns a `tool_result` block carrying the output,
and the model reads that output, *decides what to do next*, and emits the next
`tool_use`. The loop is, in symbols,

```
tool_use → tool_result → tool_use → tool_result → ...
```

with the model's *next act* decided inside each `tool_result` callback. Chat text is
what the model says to a human while this is happening. The reasoning is in the
round-trip.

Translate chat text and you have a bilingual chatbot. Translate the round-trip
faithfully and you have an agent. The two are different things, and most of the
rubber that the published model routers meet on the road is exactly here. If the seam
drops a tool id, the model cannot tell which call a result belongs to and loses the
thread. If the seam loses the `content` field on a `tool_result`, the model does not
know what the world said, and the next call is a guess. If the seam rewrites a tool
name on the way back, the model's argument parser fails and the loop stalls.

None of this is hard to state. All of it is hard to keep faithful at speed, and
faithful is what the agent needs to keep reasoning. The seam is load-bearing precisely
because that is where the agent thinks.

## A seam in the wild

A seam that is faithful in principle and unfaithful in practice is a seam that fails
under load, and the load a coding agent puts on a seam is multi-step, real I/O, and
debugging. The end-to-end test that `claude-go` ships with, the one I keep running,
is a small Rust CLI and an open-weight model, and the point of it is that the model
has to *self-diagnose* a compile error and recover.

The user runs `claude-go on --model glm-5.2`. The proxy listens on `127.0.0.1:7184`.
The user then starts `claude` pointed at the proxy and asks the model to write a
Rust CLI that reads a `urls.txt` and reports the HTTP status of each URL. The model
emits a `tool_use` to write a `Cargo.toml` with `clap`, `reqwest` (blocking), and
`tabular`. It emits a `tool_use` to write `src/main.rs`. It emits a `tool_use` to
run `cargo run --release`. The seam translates all three into the model's native
dialect. The compile fails, because `tabular` does not accept numeric width
specifiers in its format string, and the runtime hands the stderr back as a
`tool_result`. The model reads the result, decides what is wrong, and emits a
`tool_use` calling the `Update` tool to fix the format string. The seam carries the
`Update` call across, and the `Update` result back, and the model runs `cargo run
--release` again. The output is a working three-row table.

The transcript, abridged to the moment the seam is on trial, looks like this:

```
[tool_use] Write  src/main.rs
[tool_use] Bash   "cargo run --release"
[tool_result] stderr
   error[E0277]: the trait bound `std::string::String: From<Vec<...>>` is not satisfied
   --> src/main.rs:18:24
   ...
   note: tabular does not accept numeric width specifiers in the format string
[tool_use] Update src/main.rs  (id: toolu_01...)
[tool_result] ok  (the seam carried the tool id across without rewriting it)
[tool_use] Bash   "cargo run --release"
[tool_result] stdout
   +----+-------+
   | url| status|
   +----+-------+
   | ...|   200 |
   | ...|   404 |
   | ...|   200 |
   +----+-------+
```

Six tool calls, one compile error, one self-diagnosis, one fix, one working binary.
The wall time was one minute and thirty-seven seconds. The model never had to be
told what `tabular` does. The model never had to be told what the error meant. The
seam carried the round-trip across cleanly enough that the model could keep
reasoning, and the reasoning, in this case, was the work.

This is a reconstruction, not a captured log. The real run, on the box I keep
calling `dovm`, looked like the above with timestamps in the wrong place, a `cd` in
the middle, and a single moment where the model asked `Bash` to `cat Cargo.toml`
before deciding what to write. I have stripped the noise; the seam is what the
transcript is *about*.

## The in-process choice

The seam, then, is the design surface, and the next question is where the seam
*runs*. The first version of `claude-go` ran the seam in a *separate process*: a
Node.js child called `opencode-api`, launched from the CLI, listening on a port,
shuttling JSON between the client and the model. The seam was a network round-trip
to localhost, with a separate binary, a separate install surface, and a separate
failure mode. The CLI had to check whether the child had crashed. The child had to
parse its own config. The seam could die while the CLI lived, and vice versa, and
the user had to install two things to make one thing go.

Version 0.2.0 collapsed the seam into the same Rust binary that drives the CLI. The
proxy is now an in-process **axum** server, started and torn down with the command,
running on a port that the CLI owns. The seam is a function call, not a fork, and
the seam is a function call that the same process is responsible for keeping alive.
The first consequence is mechanical: one binary, 5.1 MB stripped, zero runtime
dependencies, one `curl | bash` install line. The second consequence is what the
design choice actually buys. The seam cannot die while the CLI lives, because they
are the same process. The seam cannot drift out of sync with the CLI's notion of
which model is selected, because the model is a struct field in the same binary.
The seam cannot be on a different version of the same idea, because there is only
one version.

The cost is real, and worth naming. An in-process seam is a single point of
failure for the whole tool, and a bug in the proxy takes the CLI down with it. The
proxy is no longer a thing another team can iterate on in a different language at a
different pace. The seam is welded to the CLI in a way that a child process was
not. The bet is that the seam is small enough, and well-defined enough, that this is
the right trade, and the proof is the test above. I have not always been sure of
this bet. I am now.

The seam is also a seam between the human and the machine, and the human's
environment matters. The TUI used to crash on no-args when invoked from a pipe, a
cron job, or a systemd unit, anywhere there was no TTY. The fix was a small file
called `tty.rs`, 144 lines, that gates the TUI on `TERM != "dumb" &&
stdin.is_tty() && stdout.is_tty()`, and falls back to a JSON status object
otherwise. The seam is also a trust boundary, and trust has to be marked. The first
`claude-go off` would have stripped every `ANTHROPIC_*` environment variable it
found, including the ones a user had set themselves. The fix was an in-settings
ownership marker, so that `claude-go` only undoes what `claude-go` set, and a user
who brought their own `ANTHROPIC_API_KEY` keeps it. The seam is also the build
pipeline, and pipelines fail in different ways on different platforms. The release
CI broke on Windows PowerShell three times, and three times for different reasons,
and the third time the fix was a `cross-rs` build inside a Debian `arm64v8`
container, which is a sentence I did not expect to write at the start of the year.
The point is the same point: every seam in the tool, the protocol seam, the TTY
seam, the trust seam, the build seam, is somewhere a thing can go wrong, and a tool
that survives the field is a tool whose seams are *visible to the person who has to
fix them*.

## What the seam doesn't cover

A clean accounting of what the seam does is incomplete without an honest accounting
of what it does not, and I want to be plain about three.

First, the seam covers Anthropic Messages on one side and *one* non-Anthropic shape
on the other. The battle-tested path is **OpenAI Chat Completions**, the dialect
spoken by the model that ships with the most aggressive license, the one I use to
test the seam under load, and the dialect spoken by enough of the open-weight
field that a single translation is most of the work. **Cloudflare Workers AI**,
**Google Vertex**, and **AWS Bedrock** are stubbed in the registry, with the
right config keys and the right environment variables, and the seam is not yet
written for them. Each of those shapes carries tool calls differently, and the
bet of the project is that the seam, when written, will be one more translation
function next to the others, but the bet is not yet *paid*.

Second, the seam is not a model selector. `claude-go` does not pick a model for the
user. The user picks, and the seam carries the choice across. The seam does not
implement a routing policy, a cost model, or a fallback ladder. Other tools in this
space do, and they are the right tools for the problem those problems are. The
seam is the part where, given a chosen model, the round-trip stays faithful. That
is the part `claude-go` is opinionated about, and that is the part it does.

Third, the seam does not make any claim about *quality*. A faithful seam is a seam
that does not lose information. It is not a seam that improves the model. If the
model on the other side is weaker, the agent on the other side is weaker, and a
cleaner pipe does not fix that. The bet is that the seam has been a bottleneck on
the field's ability to *know* which model is actually good at the work, because the
field has not been able to run the same agent on the same task through two
different backends and trust the comparison. A faithful seam is a measurement
instrument, and the measurements it enables are the ones that will tell us which
models are worth pointing the agent at.

---

## In closing

A model router that only moves chat text is a translation layer; a model router
that carries the tool-use round-trip is a way of letting the agent think. The
interesting design choice in routing Claude Code to a non-Anthropic model is not
the model, and it is not the CLI, and it is not the install line. It is the seam
where the two shapes meet, and the seam's only job is to be invisible to the
agent on the other side, and that invisibility, *not the model, is the work.*
